# Data Schema Documentation

## Overview

This document describes the data structure and schema for all data files used in the Subtle-Decline Dashboard system. The system uses CSV files for data storage and exchange, making it simple to deploy and integrate with existing healthcare systems.

---

## Core Data Tables

### 1. Daily Observations (`synthetic_daily_data.csv`)

**Purpose**: Contains daily patient observation data from multiple provider sources.

**Primary Key**: `patient_id` + `observation_date`

| Field Name | Data Type | Required | Description | Example Values |
|------------|-----------|----------|-------------|----------------|
| `patient_id` | String | Yes | Unique patient identifier | P001, P002, P003 |
| `patient_name` | String | Yes | Patient display name | Alice Johnson, Bob Smith |
| `observation_date` | Date | Yes | Date of observation (YYYY-MM-DD) | 2026-05-22, 2026-08-15 |
| `mobility_steps` | Integer | Yes | Daily step count | 4500, 6780, 3200 |
| `nutrition_kcal` | Integer | Yes | Daily caloric intake | 1850, 2200, 1400 |
| `participation_minutes` | Integer | Yes | Daily activity participation minutes | 45, 85, 120 |
| `data_source` | String | No | Source system identifier | Wearable Device, Manual Entry |
| `observation_quality` | String | No | Data quality indicator | Good, Fair, Poor |

**Data Constraints**:
- `patient_id`: Must be consistent across all tables
- `observation_date`: Must be valid date, no future dates allowed
- `mobility_steps`: Range 0-25,000 (reasonable daily step count)
- `nutrition_kcal`: Range 500-5,000 (reasonable daily caloric intake)
- `participation_minutes`: Range 0-300 (reasonable daily activity time)
- `observation_quality`: Must be one of [Good, Fair, Poor]

**Relationships**:
- Links to `synthetic_incidents.csv` via `patient_id`
- Links to `generated_alerts.csv` via `patient_id`

---

### 2. Incidents (`synthetic_incidents.csv`)

**Purpose**: Records major adverse events for experimental validation and analysis.

**Primary Key**: `incident_id`

| Field Name | Data Type | Required | Description | Example Values |
|------------|-----------|----------|-------------|----------------|
| `incident_id` | String | Yes | Unique incident identifier | INC001, INC002, INC003 |
| `patient_id` | String | Yes | Associated patient identifier | P001, P010, P005 |
| `incident_date` | Date | Yes | Date incident occurred (YYYY-MM-DD) | 2026-08-21, 2026-08-28 |
| `incident_type` | String | Yes | Type of adverse event | Fall, Hospitalization, Severe Malnutrition |
| `severity` | String | Yes | Incident severity level | Low, Moderate, High |

**Data Constraints**:
- `incident_id`: Must be unique across all incidents
- `patient_id`: Must exist in daily observations table
- `incident_date`: Must be valid date
- `incident_type`: Common types include Fall, Hospitalization, Emergency Visit, Severe Malnutrition, Functional Deterioration
- `severity`: Must be one of [Low, Moderate, High]

**Relationships**:
- Foreign key to `synthetic_daily_data.csv` via `patient_id`
- Used for performance evaluation against generated alerts

---

### 3. Generated Alerts (`generated_alerts.csv`)

**Purpose**: Contains all alerts generated by the decline detection engine.

**Primary Key**: `alert_id`

| Field Name | Data Type | Required | Description | Example Values |
|------------|-----------|----------|-------------|----------------|
| `alert_id` | String | Yes | Unique alert identifier | ALT_P001_20260825 |
| `patient_id` | String | Yes | Associated patient identifier | P001, P002, P003 |
| `patient_name` | String | Yes | Patient display name | Alice Johnson, Bob Smith |
| `decline_start_date` | Date | Yes | When decline pattern began | 2026-08-23 |
| `alert_date` | Date | Yes | When alert was generated | 2026-08-25 |
| `duration_days` | Integer | Yes | Length of decline period in days | 2, 3, 7 |
| `domains_affected` | String | Yes | Which domains show decline | Mobility, Nutrition, Multiple |
| `composite_score` | Decimal | Yes | Calculated decline severity (0.0-1.0) | 0.342, 0.567, 0.123 |
| `severity` | String | Yes | Alert classification | LOW, MEDIUM, HIGH |
| `mobility_delta` | Decimal | Yes | Mobility percentage change | -18.5, -5.2, 12.3 |
| `nutrition_delta` | Decimal | Yes | Nutrition percentage change | -12.8, 3.4, -22.1 |
| `participation_delta` | Decimal | Yes | Participation percentage change | -15.6, -8.9, 2.1 |
| `explanation` | String | Yes | Human-readable alert reason | Mobility declined 18.5% from personal baseline for 3 consecutive days |
| `status` | String | Yes | Alert status | ACTIVE, RESOLVED, DISMISSED |
| `created_at` | DateTime | Yes | Alert creation timestamp | 2026-08-25 14:32:15 |

**Data Constraints**:
- `alert_id`: Must be unique, format: ALT_{patient_id}_{start_date}
- `patient_id`: Must exist in daily observations table
- `decline_start_date`, `alert_date`: Must be valid dates, alert_date >= decline_start_date
- `duration_days`: Must be >= 2 (minimum consecutive days requirement)
- `composite_score`: Range 0.0-1.0
- `severity`: Must be one of [LOW, MEDIUM, HIGH]
- `mobility_delta`, `nutrition_delta`, `participation_delta`: Percentage values (can be negative)
- `status`: Must be one of [ACTIVE, RESOLVED, DISMISSED]

**Relationships**:
- Foreign key to `synthetic_daily_data.csv` via `patient_id`
- Used for performance evaluation against synthetic incidents

## Data Quality Standards

### Required Data Quality Checks

1. **Completeness**:
   - All required fields must be present
   - No missing values in critical columns
   - Minimum data density requirements (e.g., 70% of expected observations)

2. **Consistency**:
   - Patient IDs consistent across all tables
   - Date formats standardized (YYYY-MM-DD)
   - Enumerated values match allowed lists

3. **Validity**:
   - Numeric values within reasonable ranges
   - Dates are valid and not in future
   - String values conform to expected patterns

4. **Uniqueness**:
   - Primary keys are unique within each table
   - No duplicate patient-date combinations in daily observations

### Data Quality Indicators

Each observation includes quality metadata:

- **Good**: Complete, timely, validated data from primary source
- **Fair**: Complete data with minor quality concerns (e.g., delayed transmission)
- **Poor**: Incomplete or estimated data (e.g., manual entry, device malfunction)

### Missing Data Handling

1. **Missing Observations**: Clearly indicated in analysis and reporting
2. **Partial Data**: Quality score reflects completeness
3. **Stale Data**: Freshness status explicitly tracked and displayed
4. **Invalid Data**: Excluded from calculations with appropriate logging

## Integration Specifications

### CSV File Requirements

- **Encoding**: UTF-8
- **Delimiter**: Comma (,)
- **Quote Character**: Double quote (")
- **Header Row**: Required, exact column name matching
- **Date Format**: YYYY-MM-DD (ISO 8601)
- **DateTime Format**: YYYY-MM-DD HH:MM:SS
- **Decimal Places**: Up to 3 decimal places for scores and percentages

### File Naming Conventions

- `synthetic_daily_data.csv`: Daily patient observations
- `synthetic_incidents.csv`: Major adverse events
- `generated_alerts.csv`: System-generated alerts
- `alert_summary.json`: Experiment results and metrics

### Data Refresh Patterns

- **Daily Observations**: Updated daily with new observations
- **Incidents**: Added as events occur (typically infrequent)
- **Alerts**: Generated in batch processing runs
- **Summary**: Updated after each experiment execution

## Database Design (Future SQL Implementation)

When migrating from CSV to database storage, the following SQL schema could be used:

```sql
-- Patients table
CREATE TABLE patients (
    patient_id VARCHAR(10) PRIMARY KEY,
    patient_name VARCHAR(100) NOT NULL,
    date_of_birth DATE,
    enrollment_date DATE NOT NULL,
    care_coordinator_id VARCHAR(10),
    INDEX idx_coordinator (care_coordinator_id)
);

-- Daily observations table
CREATE TABLE daily_observations (
    observation_id BIGINT AUTO_INCREMENT PRIMARY KEY,
    patient_id VARCHAR(10) NOT NULL,
    observation_date DATE NOT NULL,
    mobility_steps INT CHECK (mobility_steps BETWEEN 0 AND 25000),
    nutrition_kcal INT CHECK (nutrition_kcal BETWEEN 500 AND 5000),
    participation_minutes INT CHECK (participation_minutes BETWEEN 0 AND 300),
    data_source VARCHAR(50),
    observation_quality ENUM('Good', 'Fair', 'Poor'),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (patient_id) REFERENCES patients(patient_id),
    UNIQUE KEY unique_patient_date (patient_id, observation_date),
    INDEX idx_patient_date (patient_id, observation_date),
    INDEX idx_observation_date (observation_date)
);

-- Incidents table  
CREATE TABLE incidents (
    incident_id VARCHAR(10) PRIMARY KEY,
    patient_id VARCHAR(10) NOT NULL,
    incident_date DATE NOT NULL,
    incident_type VARCHAR(50) NOT NULL,
    severity ENUM('Low', 'Moderate', 'High') NOT NULL,
    description TEXT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (patient_id) REFERENCES patients(patient_id),
    INDEX idx_patient_date (patient_id, incident_date),
    INDEX idx_incident_date (incident_date)
);

-- Generated alerts table
CREATE TABLE generated_alerts (
    alert_id VARCHAR(20) PRIMARY KEY,
    patient_id VARCHAR(10) NOT NULL,
    decline_start_date DATE NOT NULL,
    alert_date DATE NOT NULL,
    duration_days INT NOT NULL CHECK (duration_days >= 2),
    domains_affected VARCHAR(100),
    composite_score DECIMAL(5,3) CHECK (composite_score BETWEEN 0 AND 1),
    severity ENUM('LOW', 'MEDIUM', 'HIGH') NOT NULL,
    mobility_delta DECIMAL(6,2),
    nutrition_delta DECIMAL(6,2),
    participation_delta DECIMAL(6,2),
    explanation TEXT NOT NULL,
    status ENUM('ACTIVE', 'RESOLVED', 'DISMISSED') DEFAULT 'ACTIVE',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    FOREIGN KEY (patient_id) REFERENCES patients(patient_id),
    INDEX idx_patient_date (patient_id, alert_date),
    INDEX idx_alert_date (alert_date),
    INDEX idx_severity (severity),
    INDEX idx_status (status)
);
```
